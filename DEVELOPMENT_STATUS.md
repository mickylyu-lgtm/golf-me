## Two-provider real course architecture (2026-08-16)

Replaces the single-provider (Geoapify-only) course design from Phase 3 with a canonical-course-plus-mappings architecture, driven by a live finding: GolfCourseAPI (a real, free-tier course-data API Micky brought in, ~30k courses) turned out to have **no location search capability at all** — confirmed live before building anything (searching "Farmingdale," a real town with real courses, returns 0 results; searching "New York" only matches a club literally named that) and **no coordinates in its response**, only address/city/state/country text. That ruled out "replace Geoapify with GolfCourseAPI," which was the first plan, once it was clear GolfCourseAPI can't do the one thing ("nearby courses near your location") that was the actual point.

Revised, implemented architecture:
- **Geoapify stays the location-discovery provider** (`course-search` Edge Function, unchanged provider, same real/nearby search it's had since Phase 3) — it's the one of the two that can actually search by coordinates and already returns lat/lng.
- **GolfCourseAPI becomes an on-demand, best-effort enrichment provider** (`course-enrich`, new Edge Function) — given a course GolfMe already found via Geoapify, searches GolfCourseAPI by name and, on a confident match (name-token overlap AND a city/state cross-check — never attaches across a location mismatch, verified against real data below), attaches real hole-count data. Deliberately on-demand per course (never batched over a search-result list) because the free tier is 50 requests/day; `courses.golfcourseapi_checked_at` guarantees a course is ever checked at most once.
- **`public.course_external_ids`** (new table) maps a canonical `courses.id` to each provider's own id, so the same physical course found by both providers ends up as one canonical row with two mappings, never a duplicate. `upsert_external_course()` (find-or-create, for course-search) and `attach_external_course_mapping()` (attach-to-known-course, for course-enrich) are the only two sanctioned write paths — same "no direct client insert" discipline as `round_participants`.
- Extended `courses` with `normalized_name`, `address`, `holes`, `course_type`/`website`/`phone`/`description` (nullable, unpopulated for now — GolfCourseAPI's real response doesn't actually include these last three, so they're schema-ready for a future provider that does, never fabricated from thin air).
- Real-only "Entered by the host — not confirmed with the course" disclaimer added to `GolfCallDetail`'s tee-time display, and `enrichRealCourse()` fires best-effort on viewing a real round's course.
- `src/lib/teeTimeProvider.ts` (new) — a `TeeTimeProvider` interface + a `MockTeeTimeProvider` that returns nothing (never fake slots), scaffolding for a future real tee-time integration. Not wired into any UI this round, per explicit scope decision (interface/schema only, no real tee-time provider yet).

## Architectural decisions

- **Mocked-first, Supabase-second**: UI and product flows were built against a localStorage mock so product iteration wasn't blocked on backend design. Migration to Supabase happens entity-by-entity now that the shape of the data model is proven out by the mock.
- **Anon key only in the frontend, ever**: `VITE_`-prefixed env vars are inlined into the shipped bundle by Vite. The service_role/secret key must never be referenced in frontend code or committed anywhere — RLS policies are the access-control boundary, not key secrecy. See the comment header in `src/lib/supabase.ts` and `.env.example`.
- **Single repo, single `main` branch, GitHub as source of truth**: no long-lived feature branches; small commits with clear messages so any session (laptop or claude.ai/code mobile) can `git log`/`git pull` and immediately understand recent history. Push and Vercel deploy always require explicit confirmation from Micky before happening.
- **No unattended/scheduled agents**: development sessions are always actively driven (by Micky, from the laptop or from claude.ai/code in a mobile browser) — no cron-triggered or background cloud agents are configured to push commits unsupervised.
- **Reputation counters stay denormalized on `profiles` for now**: `completed_rounds`, `show_up_rate_pct`, etc. live directly on the row (same shape as the old mock) rather than being computed from a `reviews` table, since `reviews` doesn't exist yet. Revisit once reviews are migrated — likely becomes a computed/aggregated value at that point.
